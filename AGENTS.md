# AGENTS.md

## Scope

This file applies to the whole `ankhorage/renovate` repository.

`@ankhorage/renovate` owns the canonical Renovate policy and the trusted dependency-update
automation shared by standalone Ankhorage repositories. Keep dependency ownership explicit: this
repository decides what Renovate may update, while packages such as `@ankhorage/devtools` remain
the single source of truth for the repository state they generate and synchronize.

## Architectural north star: one policy, explicit owners

Ankhorage repositories are intentionally standalone. They consume one repository-hosted Renovate
preset instead of copying dependency rules locally.

The shared policy must prevent competing writers:

- Renovate updates dependencies owned by the target repository.
- Normal consumers receive released `@ankhorage/*` packages, including
  `@ankhorage/devtools`, through Renovate.
- Devtools-owned Bun metadata, toolchain configuration, and canonical workflows are changed by
  Devtools synchronization, not independently in every consumer.
- The Devtools owner repository may use an explicit owner-specific policy to update the third-party
  toolchain it publishes for consumers.
- Repository-specific workflows outside the exact Devtools-managed inventory stay repository-owned.

Do not solve an owner-specific need by broadening the default consumer policy for every repository.
When variants are required, make them explicit, published, documented, and tested.

## Canonical preset ownership

`default.json` is a published public contract. Changes affect every repository extending:

```json5
extends: ['github>ankhorage/renovate']
```

The unqualified GitHub preset reference follows the repository's default branch. It is not a pinned
package or preset version.

### Keep rules narrow and intentional

The current default policy disables dependency updates first and then explicitly enables the
supported Ankhorage package scope. Renovate merges matching `packageRules`, so rule order and later
overrides are behavior, not cosmetic formatting.

When changing the preset:

1. identify the dependency owner
2. identify the Renovate manager and datasource
3. distinguish extraction from update permission
4. preserve the default-deny boundary
5. use exact package names, paths, managers, or datasources where ownership is narrow
6. verify the effective merged configuration in tests and with Renovate's validator

Do not confuse Dependency Dashboard manager headings with update ownership:

- `bun` is the manager for Bun-backed `package.json` and `bun.lock` projects; it does not mean only
  the Bun runtime.
- `renovate-config` means Renovate detected a Renovate configuration file and any updateable pinned
  preset/tool references inside it.
- Detected files or managers do not by themselves prove that Renovate is allowed to open an update.

### Consumer and owner policies

Normal consumer policy must keep `@ankhorage/devtools` eligible for ordinary Renovate updates. A
released Devtools version is the unit consumers should receive; canonical sync then applies the Bun,
tooling, package-script, workflow, and editor policy shipped by that version.

Do not enable direct consumer updates for packages or values owned by Devtools, including its Bun
runtime contract, ESLint toolchain, Knip, Prettier, and canonical workflows.

An owner-specific Devtools policy may enable those third-party dependencies in
`ankhorage/devtools`, where compatibility is tested and released. Major toolchain updates must remain
reviewable and must not be made broadly automergeable without explicit evidence.

The canonical Devtools workflow inventory is currently:

```text
.github/workflows/ci.yml
.github/workflows/renovate.yml
.github/workflows/release.yml
```

Do not treat unknown or repository-specific workflows as Devtools-owned.

## Trusted Changeset workflow

`.github/workflows/changeset.yml` is invoked from consumer `pull_request_target` workflows with
write-capable permissions. Treat it as security-sensitive production code.

Required invariants:

- accept only `renovate[bot]`
- require a same-repository head branch beginning with `renovate/`
- inspect base and head files through the GitHub API
- never check out or execute pull-request code in the privileged context
- limit writes to the deterministic Changeset path on the validated Renovate branch
- dispatch CI for the exact updated branch after a write
- remain idempotent when the expected Changeset already exists

The workflow creates a release Changeset only when a non-private package changes an Ankhorage
dependency in `dependencies`, `optionalDependencies`, or `peerDependencies`. Dev-only Ankhorage
updates receive an empty Changeset. Preserve this distinction unless the public release contract is
intentionally changed.

Consumer workflows should call trusted reusable workflow revisions by immutable commit SHA. Do not
replace a SHA pin with a mutable branch or tag.

If future automation synchronizes Devtools-managed files on a Renovate branch, it must preserve the
same trust boundary: do not execute arbitrary PR-head code with a write token, use an exact released
first-party provider, restrict the writable file inventory, and fail on unexpected changes.

Keep preset behavior in declarative configuration and focused tests. Do not add a TypeScript runtime
abstraction merely to represent static Renovate JSON.

## Public API rules

The TypeScript root API is intentionally empty and reserved for a future `ankh renovate` provider.
Do not add exports unless there is a real, package-owned runtime capability with consumers.

When adding a public preset variant:

1. give it an explicit root-level JSON entrypoint
2. export it intentionally from `package.json` when npm consumers need it
3. add a consumer example
4. validate it with `renovate-config-validator`
5. add focused contract tests
6. document how it composes with or differs from `default.json`
7. add a changeset

Do not require consumers to deep-import unpublished files.

## Tests and validation

Run the relevant checks before handing off.

Preferred full validation:

```bash
bun run build
bun run lint:fix
bun run test
bun run knip
bun run typecheck
bun run format:check
bun run docs
bun run changeset:status
```

Notes:

- `bun run test` runs Bun tests and validates `default.json` with Renovate's config validator.
- Preset tests must assert effective ownership boundaries, not only that JSON parses.
- Workflow tests must retain negative assertions against checkout or execution of untrusted PR code.
- `bun run docs` regenerates Paradox output and `README.md`.
- Run `git diff --check` after generated or workflow changes.

## Changesets

Add a changeset for published behavior changes, including:

- changes to `default.json` or another exported preset
- changes to update grouping, eligibility, automerge, or range strategy
- changes to the trusted reusable workflow's consumer-visible behavior
- new package exports or public runtime APIs

No changeset is usually needed for:

- tests that do not change behavior
- internal refactors
- repository-only documentation such as this `AGENTS.md`
- generated documentation updates without a public contract change

Use patch unless the compatibility or behavior change clearly requires a higher bump.

## Dependency rules

This repository depends on Renovate for configuration validation and on Devtools for the shared
repository toolchain. Keep these roles separate:

- Renovate defines and validates dependency-update semantics.
- Devtools provides linting, formatting, Knip, Bun policy, and managed workflows.
- Changesets owns package release metadata.
- Paradox owns generated documentation.

Do not add dependencies to implement behavior Renovate already expresses declaratively. Do not copy
Devtools-owned toolchain packages or workflow policy into this repository as an independent source
of truth.

## Working style for agents

Before changing policy or automation:

1. inspect `default.json`, the consuming example, and relevant tests
2. identify whether the change belongs to the consumer preset, an owner-specific preset, Devtools,
   or a repository-local override
3. inspect the trusted workflow boundary when writes or `pull_request_target` are involved
4. determine whether a changeset is required
5. state which repositories and dependency classes will change behavior

While changing it:

1. keep one canonical rule for each ownership boundary
2. avoid overlapping broad rules whose merge result is difficult to reason about
3. add positive and negative contract tests
4. preserve least privilege and immutable workflow references
5. update examples and generated docs when consumer usage changes

When handing off, report the effective Renovate behavior, security impact, validation performed, and
whether consumers require a release, preset refresh, or manual Renovate rerun.
